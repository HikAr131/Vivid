# 画质管家 UI 规范 —— 1U 设计语言的 egui 落地

> 来源：1U-Hikari 的 `docs/frontend-style-guide.md`（Vue + CSS）。本文件是它在
> **egui 即时模式 GUI** 下的翻译版——原则照搬，实现方式完全不同（egui 没有 CSS、
> 没有 `backdrop-filter`、没有伪类，布局是逐帧重算的）。
>
> **配色不在本文讨论范围**：`main.rs` 里那套来自 logo 的品牌色（青 `#22D3EE` →
> 紫 `#A855F7`）是对的，沿用。本文只管**布局与交互**——那才是当前界面「丑」的根因。

---

## 0. 一句话总纲

> **一屏只有一个卡层级；卡里的东西一律扁平，靠底色分轻重，不靠画线。**

---

## 1. 当前界面的问题（2026-08-31 截图逐条对照）

先说清楚哪里不对，否则规范落不到实处。

| # | 现象 | 根因 | 规范条目 |
|---|---|---|---|
| 1 | 游戏名那一列有空行（第 2、5 行） | 用 `egui::Grid` 表格排了本该是**分组清单**的东西，分组关系只能靠「第一列留空」表达 | §3 |
| 2 | 5 个高饱和青色按钮排成一列，像一堵墙 | 主操作色被用在了**每一行**上。高饱和是稀缺资源，一屏只该有一处 | §4 |
| 3 | 「已经是最新」和按钮挤在同一列 | 状态和操作是两种东西，被塞进了同一个表格列 | §3 |
| 4 | 顶部只有显卡型号和三个能力标记 | **没有回答用户最想知道的问题**：「我这台机器有几个游戏可以升级？」结论层缺失 | §2 |
| 5 | 底部黄字常驻 | 常驻的静态说明**不是通知**，用警告色会让用户脱敏，真出事时反而看不见 | §5 |
| 6 | 行与行之间靠斑马纹分隔 | `striped(true)` 是表格的产物，视觉噪音大 | §3 |
| 7 | 只有按钮可交互，行本身没反应 | 缺整行 hover——1U 设置行的核心手感 | §6 |

**一句话概括：把一份「按游戏分组的清单」做成了「一张数据表」。**

## 2. 版式：先分层，再排版

动手前先回答：**这一屏在回答用户的什么问题？** 然后按答案分三层，
**不要**按「现在有几行数据」去排表格。

| 层 | 装什么 | 形态 | 数量 |
|---|---|---|---|
| ① **结论** | 这一屏的答案 | 状态块：结论一句话 + 副行说明，主操作放右侧 | **整屏唯一强调，最多 1 个** |
| ② **可操作** | 用户能改的东西 | 分组 + 行 | 按游戏分组 |
| ③ **只读/说明** | 事实与提示 | 灰字，不用警告色 | 放最后 |

### 这个页面应该长成什么样

```
┌─ 画质管家 ────────────────────────────────── [重新扫描] ─┐   ← 标题栏
│                                                          │
```

**关键差别**：
- 游戏名从「表格第一列」变成「组标题」——分组关系是**结构**表达的，不再需要留空行
- 版本号从独立一列变成**副行小字**，主行只留功能名
- 「已是最新」的游戏整组收敛成一个淡色状态，不再占用主操作色
- 顶部多了一句真正的结论

## 3. 禁止用 `egui::Grid` 排内容列表

**这是本项目最重要的一条布局规则。**

`Grid` 是给「真·二维表格」用的（比如对照矩阵）。用它排清单会必然产生三个问题：

1. 分组只能靠 `ui.label("")` 留空表达，弱且难看（截图里那两个空行）
2. 列宽全局对齐，右侧按钮列会被最长的那个撑开，短的显得空旷
3. `striped(true)` 斑马纹是视觉噪音，1U 那边整个设计系统里没有斑马纹

**改用「组 + 行」**：

```rust
for (game, comps) in &self.games {
    ui.group_label(game, if all_latest { "已是最新" } else { "" });
    ui.group(|ui| {
        for (i, c) in comps.iter().enumerate() {
            if i > 0 { ui.row_divider(); }     // 只在行之间画，首尾不画
            ui.row(c.kind.display_name(), &version_sub(c), |ui| {
                // 右侧：操作或状态
            });
        }
    });
}
```

行高由内容决定，每组独立对齐，分组关系由**结构**表达。

## 4. 层级与强调

| 层 | 这个项目里是什么 | 材质 |
|---|---|---|
| **L0** 窗口底 | `BG` `#0E1116` | 纯色 |
| **L1** 区块 | `PANEL` `#161B22` + 1px `LINE` 边框 | **页面唯一的卡层级** |
| **L2** 内容 | `CARD` `#1A1F27`，**无边框** | 分组容器、行、瓷砖 |
| **L3** 浮层 | 近实底 + 阴影 | 确认框、下拉 |

**铁律：L1 里面不许再出现 L1。** 同色边框叠同色边框，零对比度增益，只是多画一圈框。
分组容器（L2）**只有底色，不画边框**——它上面已经有 L1 的边框在负责「这是一块区域」。

### 高饱和色是稀缺资源

品牌青 `#22D3EE` 作为按钮填充，**一屏只该出现一处**（结论层的主操作）。

行内的「升级」按钮改用**次要样式**（淡底 + hover 换底 + 青色文字），
这样：一眼看过去，最显眼的是顶部那个「全部升级」，而不是五个平均分布的蓝块。

判据很简单：**眯起眼睛看，最亮的地方应该只有一处。**

## 5. 说明文字不用警告色

底部那句「换过文件的游戏请不要进联机」是**常驻的静态说明**，不是通知。

- 常驻黄字 → 用户三次之后就不看了 → 真出事时的警告也一起失效
- 正确形态：普通灰字（`DIM`）
- 警告色留给**偶发**的、真的有事发生的提示（安装失败、检测到破解件来源）

这条来自 1U 规范原文：*「常驻的静态说明不是通知——那就是普通说明文字」*。

## 6. 交互：整行 hover 是核心手感

现在只有按钮可交互，行本身对鼠标毫无反应，界面因此显得「死」。

### egui 即时模式的坑（必须知道，否则写不出来）

想给一行画 hover 底色，得先知道这行多高；但行高要等内容画完才知道。
直接在内容之后 `rect_filled` 会把背景**盖在文字上面**。

**解法是「占位再回填」**：

```rust
let bg_idx = ui.painter().add(egui::Shape::Noop);   // 先占一个绘制槽

let inner = ui.scope_builder(
    egui::UiBuilder::new().sense(egui::Sense::hover()),
    |ui| { /* 画内容 */ },
);

if inner.response.hovered() {
    ui.painter().set(bg_idx, egui::epaint::RectShape::filled(
        inner.response.rect, corner_radius, HOVER_BG,
    ));   // 回填到内容之前的槽位 → 背景在文字下面
}
```

**自己写行的时候照抄这个模式**，别用别的写法。

### 其余交互规则

- **按下即给反馈**，不等抬起：`visuals.widgets.active.expansion = -1.0`（轻微内缩）
- **hover 不放大**：`hovered.expansion = 0.0`。过冲只属于带动量的手势，这个工具没有
- **摘边框会带走 hover 反馈**：`bg_stroke = Stroke::NONE` 之后必须用 `bg_fill` 把反馈补回来，
  否则控件对鼠标完全没反应（1U 实际踩过这个坑）
- **耗时操作必须有可见进度**：替换 DLL 含备份 + 校验 + 回读，慢盘上有感。
  只把按钮变灰 = 界面毫无动静，用户会反复点。至少把按钮文字切成「正在替换…」

## 7. 排版

- 主行 13.5px，副行 12px，组标题 12.5px，结论标题 15px
- **版本号用等宽字体**（`monospace`），数字对齐才好扫读
- 副行小字用 `DIM`，别用正文色——层次靠明暗，不靠字号堆砌
- 一屏最多一个 15px 以上的强调，其余全是 12–13.5px

## 8. 收尾自检

改完一屏，逐条对照：

- [ ] 眯眼看，最亮处只有一个吗？
- [ ] 有没有出现「卡里套卡」（两圈同色边框）？
- [ ] 分组关系是靠结构表达的，还是靠留空？
- [ ] 鼠标划过每一行，有反馈吗？
- [ ] 常驻文字里还有警告色吗？
- [ ] 顶部回答了「用户最想知道的问题」吗？
- [ ] 每个间距、每个字号，能说出为什么吗？（说不出的就是还没改完）

## 9. 元规则

> **Nothing is random —— every spacing, timing, and alignment value is a deliberate
> choice you can defend.**
